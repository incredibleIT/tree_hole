# 产品需求文档 - 以外 RKOS（关系知识操作系统）

**作者：** Yang
**日期：** 2026-07-15

## 执行摘要

「以外」是一个公益开源的情感叙事平台，正在构建**关系知识操作系统（RKOS）**——人类关系知识的第一个开源基础设施。项目核心定位是"讲述与错过的他/她之间不可替代的故事"，通过 AI 驱动的关系知识引擎，让平台不仅能承载故事，更能**理解**故事背后的关系本质。

RKOS 回应了一个根本性矛盾：人类关系中的遗憾和智慧极其丰富，但这些知识从未被系统化。每一个"错过的故事"都是一份珍贵的关系样本，但今天它们要么消散在记忆中，要么只停留在情感共鸣层面。RKOS 通过独创的**关系基因组（Relationship Genome）**机制，将每段感情经历解构为标准化的关系特征向量，再通过知识演化引擎持续挖掘规则与模式，构建一个越用越聪明的关系知识图谱。

**双阶段运作：**

- **一阶段（知识沉淀）：** 用户上传感情遗憾经历（文字、图片、聊天记录），Story Understanding Agent 理解并抽取信息，生成关系基因组，沉淀到知识库
- **二阶段（智能建议）：** 新用户描述感情现状，RKOS 检索最相关的历史案例和经过验证的关系规则，Agent 生成个性化的、有证据支撑的建议，反馈回流形成知识闭环

**目标用户：** 一阶段为有深刻感情遗憾经历、渴望倾诉和记录的年轻人；二阶段为正在面对感情抉择、需要"过来人"智慧的人。

**项目约束：** 公益开源、单人独立开发维护、Web 优先、后端采用 Java（Spring Boot）技术栈、分层迭代由下到上逐步构建。

## 产品的独特之处

**关系基因组是核心护城河。** 市面上没有任何产品将人类关系模式结构化为可查询、可演化的知识系统。竞品的建议是一次性的（每次对话从零开始），RKOS 让知识随使用而成长（反馈驱动置信度调整、模式权重更新）。竞品的知识在模型权重中（黑盒），RKOS 的知识在图谱中（可解释、可审计）。

用户会感知到差异的时刻：收到的建议不是泛化的心理学话术，而是"有 47 段与你相似的经历，其中 31 段在某种情况下选择了某种路径，后续结果如何"——基于真实案例的、有置信度的建议。

**为什么是现在：** 大模型能力已足以支撑复杂的故事理解和信息抽取，向量数据库和知识图谱技术成熟，AI 情感陪伴市场正从"通用聊天"向"专业知识服务"升级。

## 成功标准

### 用户成功

**一阶段（知识沉淀）：**
- 用户能够顺畅地上传故事（文字为主），系统成功理解并生成结构化的关系基因组
- 用户收到"你的故事已被理解"的确认反馈，感受到被认真倾听（而非被草率归档）
- 用户上传的故事能被准确解构为关系特征（人工抽检准确率达到合理水平）

**二阶段（智能建议）：**
- 用户描述感情现状后，收到的建议基于真实相似案例而非泛化心理学话术
- 用户感受到"这个建议真的懂我的处境"的差异化体验
- 用户愿意提供后续反馈（是否采纳、结果如何）

### 业务成功

作为公益开源项目，业务成功定义为**技术影响力**：

- **3 个月：** 第一迭代完成上线，系统能接收故事并生成 Genome；开源仓库有基本的文档和演示
- **6 个月：** 知识库积累一定数量的关系基因组样本；第二迭代（向量检索）上线；开始有外部开发者关注或参与
- **12 个月：** 知识图谱覆盖多种关系模式；二阶段建议功能可用；反馈闭环初步验证知识演化能力

### 技术成功

**第一迭代验收标准：**
- MongoDB 成功存储原始故事（文字、图片等非结构化数据）
- Story Understanding Agent 能从故事中准确抽取关键信息（人物关系、时间线、冲突类型、情感模式等）
- PostgreSQL 中成功生成并存储结构化的 Relationship Genome
- 端到端流程可跑通：上传 → 理解 → 抽取 → 生成基因组

**第二迭代验收标准：**
- Embedding Service 成功将 Genome 向量化
- Milvus 中成功存储向量及其 Metadata 索引
- 语义检索能返回相关度排序的结果

**第三迭代验收标准：**
- 知识演化引擎能从积累的基因组中挖掘出规则和模式
- 知识图谱（Neo4j）可查询
- 反馈闭环能实际驱动置信度和权重的调整

### 可衡量的关键指标

| 指标 | 目标 |
|------|------|
| 第一迭代端到端成功率 | 故事上传到 Genome 生成的完整流程通过率 ≥ 90% |
| Genome 抽取准确率 | 人工抽检关键信息抽取准确率 ≥ 80% |
| 知识库样本量（6 个月） | ≥ 100 条结构化关系基因组 |
| 向量检索相关度（第二迭代） | Top-5 结果的人工评估相关度 ≥ 70% |
| 开源社区基础 | 完整文档 + 演示 + 可复现的部署流程 |

## 产品范围与分阶段开发

### MVP 策略

**MVP 类型：概念验证型 MVP**

MVP 目标不是获取用户或收入，而是**验证核心假设**：大模型能否从个人关系叙述中准确抽取结构化的关系特征（Genome）。

**验证的核心问题：**
1. LLM 能否从非结构化的关系故事中抽取有意义的关系特征？
2. 抽取出的 Genome 是否具有足够的区分度和一致性？
3. 双存储架构（MongoDB + PostgreSQL）能否有效支撑数据管线？

**支撑的核心旅程：** 旅程一（小林的故事——完整提交路径）、旅程四（Yang 的运维排查）

### MVP 功能集（第一迭代）

| 能力 | 说明 |
|------|------|
| 故事提交 API | `POST /api/v1/stories`，接收文本故事 |
| Story Understanding Agent | LLM 驱动的信息抽取，核心创新验证 |
| MongoDB 原始故事存储 | 非结构化数据持久化 |
| PostgreSQL Genome 存储 | 结构化数据持久化 |
| Genome 查询 API | `GET /api/v1/genomes`，验证数据完整性 |
| 健康检查 API | 基本可运维性 |
| Docker Compose 部署 | 一键启动完整服务 |
| API 文档 | 开源项目可用性基础 |

**MVP 明确排除：** 前端 UI、用户账户系统、Agent 多轮追问、向量化检索、知识演化、建议生成。

### 后续迭代

| 迭代 | 核心能力 | 支撑的旅程 |
|------|----------|------------|
| 第二迭代 | Embedding Service + Milvus 向量检索 | 旅程三（阿杰的知识检索） |

- 多模态深度分析（图片/语音情感识别）

### 风险缓解策略

**技术风险：**
- **最大挑战：** Story Understanding Agent 的抽取质量——整个项目的基石
- **缓解：** 第一迭代聚焦纯文本故事，从简单 Prompt 开始逐步迭代
- **后备：** 即使 LLM 抽取不完美，结构化数据本身仍有价值（可作为人工标注基础）

**市场风险：**
- **最大风险：** “关系知识”概念需要市场教育
- **缓解：** 用具体案例演示；开源降低尝试门槛
- **验证：** 第一迭代完成后邀请 10-20 个用户试用

**资源风险：**
- **最大风险：** 单人开发，进度可能慢于预期
- **缓解：** 严格控制 MVP 范围；优先保证端到端流程跑通
- **后备：** 时间极度紧张时可先用 Python/LLM 脚本验证核心概念

## 用户旅程

### 旅程一：知识贡献者——“小林的故事”（主路径）

**开场：** 小林，25 岁，三个月前和相恋四年的女友分手了。他一直在想要不要挽回，但又说不清问题出在哪。他听说了「以外」，决定把自己的故事写下来。

**发展：**
1. 小林通过 API（或未来的前端界面）提交自己的故事——用文字描述了他们如何认识、在一起时发生了什么、分手的原因、自己现在的感受
2. Story Understanding Agent 开始理解这个故事：识别人物关系（小林和前女友）、时间线（四年恋爱）、冲突类型（沟通减少、价值观分歧）、情感模式（遗憾、不舍、自我怀疑）
3. 系统生成 Relationship Genome——将小林的故事解构为标准化的关系特征向量
4. 原始故事存入 MongoDB，结构化 Genome 存入 PostgreSQL

**高潮：** 系统返回确认：“你的故事已被理解”——附带一份摘要，显示系统从中提取了哪些关键信息。小林看到后感到“它真的读懂了我的经历”。

**结局：** 小林的故事成为知识库中的一个样本，未来可能帮助到其他经历相似的人。

**此旅程揭示的能力需求：** 故事提交接口、Story Understanding Agent（LLM 驱动的信息抽取）、MongoDB 存储、PostgreSQL Genome 存储、处理确认反馈

### 旅程二：知识贡献者——边界情况——“小陈的模糊叙述”

**开场：** 小陈，28 岁，提交了一段很简短、很模糊的故事：“我们在一起三年，后来就散了，我也说不清为什么。”

**发展：**
1. Story Understanding Agent 收到信息量很低的输入
2. Agent 识别到关键信息缺失（时间线不清晰、冲突类型未知、人物关系模糊）
3. Agent 发起追问：“你愿意多说说你们是怎么走到一起的吗？”“分开的时候，最让你难受的是什么？”
4. 小陈补充了一些细节，但依然不够完整

**高潮：** 系统基于有限信息生成了部分 Genome（标记为低置信度），同时告知小陈哪些维度的信息还不够充分。

**结局：** 即使信息不完整，这个故事仍然为知识库贡献了一份样本。系统诚实标注了不确定性，而非强行填充。

**此旅程揭示的能力需求：** Agent 追问机制（多轮对话）、低置信度处理、信息不完整时的优雅降级、Genome 的置信度标记

### 旅程三：开源开发者——“阿杰想基于 RKOS 做二次开发”

**开场：** 阿杰是一个独立开发者，正在做一个心理咨询助手 App。他发现了 RKOS 的开源仓库，想通过 API 调用关系知识图谱来增强自己产品的建议质量。

**发展：**
1. 阿杰在 GitHub 上找到 RKOS 仓库，阅读 README 和文档
2. 他用 Docker Compose 在本地启动了完整的 RKOS 服务
3. 他阅读 API 文档，尝试调用知识检索接口
4. 他成功获取了与自己测试案例相关的关系模式和建议

**高潮：** 阿杰发现 RKOS 的知识图谱提供了比通用 LLM 更精准的关系洞察，决定将其集成到自己的产品中。

**结局：** RKOS 获得了一个外部使用者和潜在的贡献者。阿杰可能会在使用中发现 bug 或提交 PR。

**此旅程揭示的能力需求：** 完整的开源文档、可复现的部署流程（Docker）、开放 API、API 文档和使用示例

### 旅程四：系统维护者——“Yang 需要排查一个问题”（运维视角）

**开场：** 作为项目的唯一维护者，Yang 收到反馈说某个故事生成的 Genome 明显不合理。

**发展：**
1. Yang 通过 API 查询到该故事的原始内容（MongoDB）和对应的 Genome（PostgreSQL）
2. 他对比了 Agent 抽取的结果和原始故事，发现 Agent 将“冷暴力”误识别为“性格不合”
3. 他检查了 Agent 的 Prompt 配置，调整了冲突类型的识别规则
4. 他重新运行该故事的处理流程，验证修正后的结果

**高潮：** 修正后的 Genome 更准确地反映了故事内容。Yang 将这个修正同步到向量索引中。

**结局：** 系统的数据质量得到改善。Yang 意识到需要更好的监控和异常检测机制。

**此旅程揭示的能力需求：** 数据查询和管理接口、Agent 配置可调、重新处理机制、数据一致性维护、基本的监控和日志

## 领域特定需求

### 数据隐私与保护

- 用户上传的故事包含极其私密的个人信息（情感经历、对话记录、照片）
- 需要对原始故事数据进行加密存储（MongoDB 加密字段或应用层加密）
- Genome 结构化数据同样属于敏感信息，PostgreSQL 中需要适当的访问控制
- 用户应有权要求删除自己的故事和 Genome（“被遗忘权”）
- 开源项目需明确数据使用政策——故事数据是否用于训练、是否匿名化
- API 调用需有身份验证和权限控制，防止未授权访问

### AI 伦理与责任

- Story Understanding Agent 的信息抽取结果可能影响用户对自身关系的认知
- 必须明确标注“这是 AI 分析结果，不是专业心理咨询”的免责声明
- Agent 不应给出具有伤害性的建议（如鼓励暴力行为、自残等）
- 置信度机制不仅是技术指标，也是伦理保障——低置信度时应明确告知用户
- 系统需要基本的有害内容过滤（识别并拒绝处理明显违规内容）

### 内容安全

- 用户可能上传包含暴力、自残倾向或其他有害内容的故事
- 系统需要有基本的内容安全审查机制（关键词检测 + LLM 辅助判断）
- 检测到高风险内容时，应提供心理健康资源链接而非简单拒绝
- 存储的故事需有内容分级标记，供后续使用场景过滤

### 技术约束

- LLM API 调用有成本和速率限制，需要合理的调用管控和成本监控
- 向量检索（第二迭代）需要处理高维数据的性能优化
- MongoDB 和 PostgreSQL 之间需要保持数据一致性（故事 ID 关联）
- 作为单人维护的开源项目，架构复杂度需要控制——优先选择成熟方案而非前沿技术
- Docker 部署需要确保服务编排的可复现性和稳定性

### 风险缓解

| 风险 | 缓解策略 |
|------|----------|
| LLM 产生不准确或有害的分析 | 置信度标注 + 免责声明 + 输出过滤 |
| 用户隐私泄露 | 加密存储 + 访问控制 + 删除机制 |
| LLM API 成本失控 | 调用频率限制 + 成本监控 + 缓存策略 |
| 开源项目被滥用 | 明确的使用条款 + API 认证 |
| 双存储数据不一致 | 关联 ID 设计 + 一致性校验机制 |
| 单人维护压力过大 | 简化架构 + 自动化测试 + 完善文档 |

## 创新与新颖模式

### 检测到的创新领域

**1. 关系基因组（Relationship Genome）——核心创新**

这是一个全新的数据模型概念：将人类关系经历结构化为标准化的特征向量。目前没有任何产品或学术工作将个人关系模式编码为可查询、可比较、可演化的结构化数据。这不是简单的“关系标签”，而是一个多维度的关系特征空间。

- **被挑战的假设：** “关系经历太主观、太独特，无法被结构化”
- **为什么可能成功：** 大模型的信息抽取能力使得从非结构化叙述中提取结构化特征成为可能

**2. 知识演化引擎——从静态存储到活知识**

传统的知识库是静态的（存入即冻结）。RKOS 的知识演化引擎通过反馈闭环持续调整规则置信度和模式权重，让知识系统“活起来”——越用越准确。这类似于生物进化中的自然选择，但应用在关系知识上。

- **被挑战的假设：** “AI 建议系统只能通过重新训练模型来改进”
- **为什么可能成功：** 知识图谱 + 置信度权重机制可以在不重新训练的情况下实现知识更新

**3. 双路径知识生成（Embedding + Rule/Pattern Agent）**

知识演化不是单一路径：一条路径是向量化语义相似度（“什么经历和你的最像”），另一条路径是规则挖掘（“什么模式在什么情况下导致了什么结果”）。两条路径互补——向量检索捕捉表面相似性，规则挖掘捕捉深层因果性。

**4. 开源关系知识基础设施**

将关系知识作为一个可复用的开源基础设施对外提供，这在定位上是全新的。不是做一个 App，而是做一个“基础设施层”——类似 PostgreSQL 之于关系型数据库，RKOS 试图成为关系知识的标准存储和查询层。

### 市场背景与竞争格局

**当前竞品状态：**
- 情感类 App（如测测、CoupleAI）停留在通用 LLM 对话，无结构化知识积累
- 心理咨询平台是人工服务，不可规模化
- 知识图谱在医疗、金融领域已有应用，但在“关系”这个领域是空白

**创新验证的市场空白：** “关系知识”作为一个独立的知识品类，目前没有任何成熟的竞品。这是蓝海，也意味着需要教育市场。

### 验证方法

**关系基因组验证（第一迭代核心）：**
- 人工抽检：对 100 个样本的 Genome 进行专家评估，验证抽取准确性 ≥ 80%
- 一致性检验：同一故事多次处理，检验 Genome 输出的稳定性
- 区分度检验：不同故事应产生明显不同的 Genome

**知识演化验证（第三迭代）：**
- 反馈闭环是否能实际驱动权重变化
- 经过演化后的知识是否比未演化时提供更准确的建议
- A/B 测试：使用演化知识 vs 静态知识的建议质量对比

### 创新风险与缓解

| 创新风险 | 缓解策略 |
|----------|----------|
| 关系基因组模型设计不当，无法捕捉真实关系复杂性 | 渐进式迭代维度设计；先覆盖核心维度，逐步丰富 |
| 知识演化引擎可能过拟合少数反馈 | 设置演化步长上限；引入多样性约束 |
| 市场对“关系知识”概念不理解 | 先用具体案例演示价值；开源降低尝试门槛 |
| LLM 抽取结果不够稳定 | 多轮验证 + 置信度标注 + 人工校准 |

## Web 应用特定需求

### 项目类型概览

RKOS 是一个**API 优先的 Web 应用**——第一迭代以后端 API 为核心，前端界面在数据模型明确后开发。这种策略的优势是：先验证核心数据管线（故事 → Genome），再投入用户界面。

项目类型混合了两个维度：
- **API 后端：** 故事提交、Genome 查询、知识检索等核心能力通过 RESTful API 暴露
- **Web 应用：** 未来需要面向用户的前端界面（React + Vite，已有原型基础）

### 技术架构考量

**后端 API 架构：**
- 框架：Java（Spring Boot）
- API 风格：RESTful，JSON 格式
- 双存储访问：MongoDB（原始故事）+ PostgreSQL（Genome），通过服务层统一暴露
- API 版本管理：第一迭代使用 `/api/v1/` 前缀，为未来演进预留空间

**API 端点规划（第一迭代）：**

| 端点 | 方法 | 描述 |
|------|------|------|
| `/api/v1/stories` | POST | 提交新故事 |
| `/api/v1/stories/{id}` | GET | 查询故事详情 |
| `/api/v1/stories/{id}/genome` | GET | 查询故事对应的 Genome |
| `/api/v1/stories/{id}/reprocess` | POST | 重新处理故事（运维用） |
| `/api/v1/genomes` | GET | 查询 Genome 列表（支持过滤） |
| `/api/v1/health` | GET | 健康检查 |

**认证模型：**
- 第一迭代：简单的 API Key 认证（开源项目，降低使用门槛）
- 未来演进：OAuth 2.0（面向终端用户时需要用户认证）

**数据格式：**
- 请求和响应统一使用 JSON
- 故事提交支持 multipart/form-data（未来包含图片上传）
- 分页采用 cursor-based（适合知识库场景）

**速率限制：**
- 第一迭代：基本的请求频率限制（防滥用）
- LLM 调用单独计数和限流（成本控制）

**前端考量（未来迭代）：**
- 技术栈：React + Vite + TypeScript（已有原型）
- SPA 架构（单页应用）
- SEO 需求：低（主要是工具型产品，非内容展示型）
- 无障碍级别：基本合规即可（公益项目，优先功能）
- 部署：GitHub Pages（静态前端）+ 独立后端服务

### 实现考量

**部署架构：**
- 前端：GitHub Pages（静态站点）
- 后端：Docker Compose 编排（Spring Boot + MongoDB + PostgreSQL）
- 一键启动：`docker-compose up` 即可运行完整服务

**可观测性：**
- 结构化日志（Java logging 框架）
- 基本的健康检查端点
- API 调用统计（请求数、延迟、错误率）

**SDK 策略：**
- 第一迭代：不提供 SDK，仅提供 REST API + 文档
- 未来：根据社区需求考虑提供 Java/Python SDK

## 功能需求

### 故事管理

- FR1：故事贡献者可以通过 API 提交一段文字故事
- FR2：系统可以在接收到故事后存储原始内容（非结构化）
- FR3：故事贡献者可以通过故事标识查询已提交的故事详情
- FR4：系统可以对已存储的故事进行重新处理（运维操作）
- FR5：系统维护者可以按条件过滤和查询故事列表

### 故事理解与基因组生成

- FR6：系统可以通过 Agent 从故事中抽取人物关系、时间线、冲突类型、情感模式等结构化特征
- FR7：系统可以将抽取结果生成为标准化的关系基因组（Genome）
- FR8：系统可以为 Genome 的各维度标注置信度
- FR9：系统可以在信息不充分时生成部分 Genome 并标注低置信度
- FR10：系统可以在处理完成后返回确认摘要，展示抽取到的关键信息

### 基因组管理

- FR11：系统可以持久化存储结构化的 Genome 数据
- FR12：外部调用者可以通过 API 查询 Genome 列表（支持分页和过滤）
- FR13：外部调用者可以通过故事标识查询对应的 Genome

### API 与认证

- FR14：系统可以通过 RESTful API 暴露所有核心能力
- FR15：系统可以通过 API Key 进行基本的身份验证
- FR16：系统可以对 API 请求进行速率限制
- FR17：系统可以对 LLM 相关调用进行独立的限流和计数
- FR18：系统可以支持 API 版本管理

### 内容安全

- FR19：系统可以对提交的故事内容进行安全审查（识别有害内容）
- FR20：系统可以在检测到高风险内容时提供心理健康资源链接
- FR21：系统可以为存储的故事标注内容安全分级

### 数据隐私与用户权利

- FR22：系统可以对敏感数据进行加密存储（列为第二迭代，MVP 阶段暂不实施）
- FR23：故事贡献者可以请求删除自己的故事和对应的 Genome
- FR24：系统可以明确标注 AI 分析结果的免责声明

### 运维与可观测性

- FR25：系统可以提供健康检查端点
- FR26：系统可以记录结构化的操作日志
- FR27：系统维护者可以调整 Agent 的 Prompt 配置
- FR28：系统维护者可以对指定故事触发重新处理流程

### 部署与可复现性

- FR29：系统可以通过一键命令启动完整的开发/演示环境
- FR30：系统可以提供完整的部署文档和使用说明
- FR31：系统可以提供 API 文档和使用示例

## 非功能需求

### 性能

- NFR1：故事提交 API（不含 LLM 处理）的响应时间应在 2 秒以内
- NFR2：Story Understanding Agent 的端到端处理（从故事接收到 Genome 生成）应在 60 秒以内完成（含 LLM 调用）
- NFR3：Genome 查询 API 的响应时间应在 500 毫秒以内
- NFR4：系统应支持至少 10 个并发故事处理请求

### 安全性

- NFR5：所有 API 通信应使用 HTTPS 加密传输
- NFR6：API Key 应通过安全方式存储（非明文），支持轮换
- NFR7：系统应记录所有数据访问和修改操作的审计日志
- NFR8：用户删除请求应在 24 小时内完成，包括所有关联数据的清除
- NFR9：敏感数据的加密存储暂不实施，列为第二迭代优先事项

### 可扩展性

- NFR10：系统架构应支持从单机部署平滑迁移到多实例部署（无需代码改造）
- NFR11：MongoDB 和 PostgreSQL 的数据量应支持 10,000 条故事/Genome 的规模而不影响查询性能
- NFR12：LLM 调用应支持可配置的模型提供商切换（避免单一供应商锁定）

### 集成

- NFR13：系统应通过标准 REST API 与外部系统集成（无需 SDK 依赖）
- NFR14：Docker Compose 编排应确保一键启动即可运行（`docker-compose up` 零配置）
- NFR15：LLM 接口应抽象为可插拔的服务层，支持不同模型的切换

### 可靠性

- NFR16：端到端故事处理流程的成功率应达到 90% 以上
- NFR17：LLM 调用失败时，系统应自动重试（最多 3 次），并将失败的故事加入重试队列
- NFR18：系统应提供清晰的健康检查端点，返回所有依赖组件（数据库、LLM 服务）的状态

### 可维护性

- NFR19：代码库应提供完整的项目结构说明和开发指南
- NFR20：Agent 的 Prompt 配置应外置于配置文件中，支持运行时调整（无需重新部署）
- NFR21：所有 API 应有自动化测试覆盖（覆盖率 ≥ 80%）
