## 挑战与成长

### 1. Spring Boot 4.1.0 包路径变更（影响 4 个 Story）

**问题：** Spring Boot 4.1 自动配置类大规模迁移到新包路径，包括：
- JDBC 自动配置 → `org.springframework.boot.jdbc.autoconfigure`
- MongoDB 自动配置 → `org.springframework.boot.mongo.autoconfigure`
- Flyway 需使用 `spring-boot-starter-flyway` 而非 `flyway-core`

**根因：** Spring Boot 4.x 是 2026-06-10 刚发布的新版本，在线文档和示例仍以 3.x 为主

**学到的：** 每次使用新版本框架时，应先用 `grep` 搜索实际 jar 包中的类路径，而非依赖文档

### 2. 测试基础设施不稳定性（影响 3 个 Story）

**问题：**
- flapdoodle 嵌入式 MongoDB 无 Spring Boot 4.x 专用 artifact，使用 `spring3x` 4.21.0
- `@DataMongoTest` 包路径变更导致测试配置失效
- `@DataMongoTest` + `@MapperScan` 冲突需通过 `MongoTestMapperFixConfig`（BeanDefinitionRegistryPostProcessor）解决

**根因：** 测试库对新版本 Spring Boot 的适配滞后

**学到的：** 测试基础设施应作为 Story 1-1 的一部分充分验证，而非在每个 Story 中反复发现问题

### 3. Docker Compose dev 环境「建而未用」

**问题：** Story 1-9 构建了完整的 Docker Compose 开发环境方案，但本地开发仍使用手动命令启动服务

**根因：** 缺乏「切换验证」这个显式步骤

**决策：** 不需要新增 Story 来推动使用，而是作为 Epic 2 开发前的前置验证行动项

## 关键洞察

### 洞察 1：新版本框架的「文档真空期」是最大风险源

Spring Boot 4.1.0 在 Epic 1 期间造成了最多的额外工作。当技术基线选择最新版本时，必须接受「文档和生态尚未就绪」的现实。应对策略：以实际 jar 包内容为准，而非文档或示例。

### 洞察 2：测试基础设施应视为一等公民

测试库的兼容性问题在 3 个 Story 中反复出现。建议将测试基础设施的充分验证纳入第一个 Story 的验收标准。

### 洞察 3：已建成的基础设施应尽快投入使用

Docker Compose dev 环境的「投资未回收」是一个典型案例。每个 Story 交付的基础设施应在下一个 Story 中立即使用，避免堆积「技术债」。

### 洞察 4：细粒度 Story 拆分是 Epic 1 成功的核心

每个 Story 独立可验证、范围明确、defer 链清晰。这种纪律性是 9/9 交付的根本保障。

### 验证 1：Docker Compose 开发环境实际启用

**结论：通过**

| 项目 | 结果 |
|------|------|
| MongoDB 7 启动 | 正常（端口 27017） |
| PostgreSQL 16 启动 | 正常（端口 5432） |
| 应用启动 | 正常（修复 Jackson 问题后） |
| 测试通过 | 57/57 全部通过 |

**发现与修复：**

1. **端口冲突**：本地已有独立 Docker 容器 `rkos-mongo`/`rkos-postgres` 运行，停止并移除后 Compose 正常启动
2. **PostgreSQL 镜像不可用**：本地无 `postgres:16-alpine`，修改 `docker-compose.yml` 为 `postgres:16`
3. **Jackson 2.x ObjectMapper 缺失（关键问题）**：
   - **根因**：Spring Boot 4.1 默认使用 Jackson 3.x（`tools.jackson`），不再自动创建 Jackson 2.x（`com.fasterxml.jackson`）的 `ObjectMapper` bean
   - **修复**：新增 `Jackson2Config.java`（`src/main/java/com/rkos/config/`），手动注册 Jackson 2.x `ObjectMapper`，配置 `JavaTimeModule`、禁用时间戳格式、忽略未知属性
   - **为什么不用 Jackson 3.x**：Spring AI SDK（`openai-java-core:4.39.1`）和 MyBatis-Plus 3.5.16 的 `JacksonTypeHandler` 均硬依赖 Jackson 2.x API，无法迁移

**代码变更：**
- 新增：`src/main/java/com/rkos/config/Jackson2Config.java`
- 修改：`docker-compose.yml`（`postgres:16-alpine` → `postgres:16`）

### 验证 3：JSONB TypeHandler 原型验证

**结论：通过（需自定义 TypeHandler）**

| 检查项 | 结果 |
|--------|------|
| MyBatis-Plus 内置 `JacksonTypeHandler` | **不兼容** PostgreSQL JSONB |
| 自定义 `JsonbTypeHandler` | **兼容**，4/4 测试通过 |
| `@TableName(autoResultMap = true)` | **必需**，否则查询时 JSONB 列不经过 TypeHandler |

**发现与方案：**

1. **内置 `JacksonTypeHandler` 失败原因**：使用 `VARCHAR` 类型传参，PostgreSQL 不接受 `varchar → jsonb` 的隐式转换
   - 错误：`column "genome_data" is of type jsonb but expression is of type character varying`
2. **自定义 `JsonbTypeHandler` 方案**：
   - 继承 `BaseTypeHandler<Object>`，使用 `ps.setObject(i, json, Types.OTHER)` 写入
   - 读取时使用 `MAPPER.readValue(json, type)` 反序列化
   - `Types.OTHER` 是 PostgreSQL JDBC 驱动识别 JSONB 的关键
3. **实体配置要求**：
   - `@TableName(autoResultMap = true)` 必须设置
   - `@TableField(typeHandler = JsonbTypeHandler.class)` 标注 JSONB 字段

**Story 2-3 关键情报：**
- 需要创建生产级 `JsonbTypeHandler`（放在 `com.rkos.common.handler` 包下）
- 实体类必须配置 `autoResultMap = true`
- 原型验证的 4 个测试用例（写入、读取、null 处理、复杂嵌套对象）可作为 Story 2-3 测试参考
